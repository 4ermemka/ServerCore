# Ход, планирование и игровая сессия

## Запуск и управление

Первый экран в `Assets/Scenes/Test.unity` предлагает **Создать сервер** или **Подключиться**.
В обоих случаях пользователь этой сборки получает роль ведущего и может управлять любой фигуркой.
Host запускает TCP-сервер и свой локальный клиент; другой ведущий подключается обычным клиентом.
Адрес, порт и локальный профиль задаются на экране. Для двух копий приложения на одном компьютере
нужны разные профили; при переподключении выбирайте прежний профиль.

- Нажмите на персонажа или мебель: снизу откроется его план.
- Перетащите фигурку на другую ячейку: добавится шаг движения. Расстояние и стоимость не ограничены;
  адрес должен существовать в сетке текущей сцены. Фактическая `Cell` пока не меняется.
- Круг, стрелка и номер показывают очередной шаг. Фигурка показывает последнюю запланированную позицию.
  Ведущий видит планы всех объектов.
- Нажмите квадрат шага: он и весь следующий за ним хвост отменятся.
- **Подтвердить ход** подтверждает текущую ревизию общего плана. Когда подтвердили все подключённые
  участники, действия исполняются и начинается следующий ход. Любое редактирование сбрасывает
  подтверждения. Ничего не запланировавший участник тоже подтверждает ход.
- Отключённый участник не блокирует завершение хода. Его принятые шаги сохраняются и исполняются
  вместе с остальными. При возвращении он получает актуальный мир, свои данные и роль по ClientId.
- В верхней панели можно загрузить сцену из Build Settings, в том числе перезагрузить текущую.
  Смена сцены отменяет старые планы, начинает новый ход и берёт стартовые объекты новой сцены.

## Границы систем

| Слой | Ответственность |
| --- | --- |
| `Shared/TurnPlanningSystem` | Чистые C# DTO, связные планы, права, подтверждения, реестр обработчиков, движение |
| `World/Data` | `WorldState` v3: сцена, коллекции объектов, участники и планы |
| `World/Planning` | Адаптер игрового мира и атомарное исполнение хода |
| `World/Game` | Сессионный lifecycle, контракты сети/ввода, привязка сцены и существующих prefab |
| `World/Presentation` | Меню, палитра и регистрируемые фабрики сценовых маркеров |
| `DmNetworkController` | Реализация `IGameNetworkSession` поверх существующего TCP и файловых identity stores |

Ядро не знает о MonoBehaviour, Unity UI, GameObject, сетевых сокетах или конкретной сцене.
`GridObjectDrag` обращается к `IWorldInteraction`. `GameSessionController` обращается к
`IGameNetworkSession`, а обработчики действий — к `IPlanningWorld` / `IGridPlanningWorld`.

## Данные и порядок

`WorldState.Scene` содержит путь scene asset и ревизию. Ревизия позволяет перезагрузить тот же путь.
`Players` и `Furniture` содержат стабильные ID, DefinitionId, подтверждённую Cell, OwnerId, DisplayName,
относительные поворот/масштаб и расширяемый словарь строковых Parameters. Ассеты и ссылки Unity
в данные не входят; абсолютное исходное оформление остаётся в prefab.

`WorldState.Planning` — один `Sync<PlanningState>`. Словарь `Plans` сопоставляет ID объекта с
**`LinkedList<PlannedAction>`**. Каждый шаг хранит собственный ID, ActionId, ObjectId, постоянный
ClientId автора, глобальный Sequence, клиентский ClientSequence, индекс цвета и Arguments.
Порядок исполнения всех объектов — глобальный Sequence; порядок автора восстанавливается по
ClientId/ClientSequence. Порядок внутри объекта представлен именно связным списком.

DTO после публикации нельзя изменять на месте. `TurnPlanner` копирует их, меняет копию и возвращает
новое значение для Sync. При добавлении/удалении команды передают Turn и ExpectedTail; при подтверждении —
Turn и Revision. Устаревшая команда отклоняется, а уже принятые шаги сохраняются. Подтверждения не меняют
ревизию содержимого, поэтому одновременное подтверждение нескольких клиентов допустимо.

`OwnerAccessPolicy` разрешает ведущему любой объект, обычному участнику — только объект с его OwnerId.
В этой сборке `WorldTurnAuthority.SetConnected` всегда назначает IsGameMaster=true.

## Команды и патчи

1. Ввод отправляет `CommandMessage` с RequestId и JSON команды. ClientId не принимается из JSON:
   сервер берёт его из прошедшего handshake соединения.
2. `GameServer.Update` передаёт `ClientCommand` игровому менеджеру на Unity-потоке.
3. Host последовательно проверяет команду и присваивает `Planning.Value`. Только его identity может
   публиковать патчи в игровой сессии. У Generic GameServer этот режим включается optional `patchAuthority`.
4. `GameClient` Host автоматически отправляет патч. `FlushLocalChangesAsync` ждёт его подтверждения;
   затем ответ команды ставится в сериализованную очередь сервера. Клиент получает данные **до** ответа.
5. Меню снимает ожидание по RequestId. Отказ содержит причину; произвольного optimistic-изменения Data
   на удалённом клиенте нет. Повторный RequestId обрабатывается из ограниченного кеша ответов сессии.
6. Когда все подтвердили, `WorldTurnAuthority` создаёт отдельную копию мира и исполняет зарегистрированные
   обработчики на ней. Ошибка не публикует частичные изменения. Успешный результат вместе с новым ходом
   передаётся одним атомарным патчем `$world` через `WorldState.PublishSnapshot`.

Host устанавливает `ApplyOwnPatchEchoes=false`: отложенное эхо его более ранней локальной записи служит
подтверждением и не откатывает более позднее состояние. У обычного GameClient поведение по умолчанию
сохранено. Все изменения Data и игровые события выполняются на одном потоке; async используется только
на границах сетевого I/O. Планирование, обработка действий и загрузка scene выполняются синхронно.

## Расширение действий

Зарегистрируйте `IPlanAction` в `GameSessionController.Actions`. Обработчик содержит стабильный ID,
проверку входных параметров без изменений мира и Execute для транзакционной копии. Для функций подходит
`DelegatePlanAction`. `MovementAction` — обычная регистрация `move`, ядро не содержит ветвлений по нему.

Для отображения зарегистрируйте в `Presentations` тот же ID и `PlanPresentation`:

- `Label(step)` — подпись квадрата меню;
- `Project(step, previousCell)` — позиция preview после шага; действие без перемещения возвращает previousCell;
- `CreateVisual(context)` — создаёт своё отображение и возвращает IDisposable для удаления.

Реестры поддерживают регистрацию во время работы. Каталог обработчиков и соответствующих представлений
должен присутствовать на всех участниках. Нет сетевой загрузки исполняемого кода.

Существующий `InteractionSystem` остаётся контрактом немедленного взаимодействия. Его `IInteraction.Execute`
можно вызывать из `DelegatePlanAction`, создавая Source/Target для транзакционной Data. Unity-объекты и
побочные внешние эффекты нельзя менять в таком Execute: откат относится к копии данных мира.
Дополнительная цель атаки или взаимодействия помещается в Arguments; ядро плана менять не требуется.

`PlanPalette` — asset `Assets/Data/Planning/PlanPalette.asset`. Host выбирает случайный свободный индекс,
сохранённый в шаге: поэтому цвета одинаковы на клиентах и сохраняются при reconnect. После исчерпания
авторских цветов палитра детерминированно дополняется уникальными оттенками. Повторяющиеся авторские
цвета считаются ошибкой настройки. Цвета уникальны внутри плана одного объекта.

## Жизненный цикл Unity

1. `Game Session` содержит persistent `WorldDataHolder`, сетевой адаптер, `GameSessionController`
   и создаваемый UI. Повторный экземпляр этой root при загрузке сцены уничтожается.
2. `WorldSceneController` получает тот же holder и `IWorldInteraction` до Initialize/Start.
   Исходный тестовый мир заполняется существующими Player/PileOfBoxes prefab.
3. Snapshot на клиенте заменяет Data. После Ready клиент загружает указанную сцену даже при прежнем
   пути; это же происходит при reconnect. Смена Path/Revision загружает её у всех.
4. Камера, GridProvider, InputManager и ManagersHolder принадлежат сцене и выгружаются вместе с ней.
   Долгоживущим остаётся только root сессии. Новый sceneLoaded заново связывает View с постоянной Data.
5. При смене сцены Host один раз заселяет новый мир авторскими объектами. Клиенты ожидают его патчи;
   пустой snapshot не запускает повторное заселение.
6. Смена Data помечает представление для обновления. Изменение выделения/меню отдельно от изменения
   мира: начало переноса не отменяется собственной перерисовкой выделения.
7. При отключении перенос отменяется, меню предлагает повторное подключение. Потеря локального клиента
   Host закрывает его серверную сессию; автоматического переноса игрового Host на другой компьютер нет.
8. Уничтожение снимает события, закрывает транспорт, удаляет маркеры и освобождает material.

События `SelectionChanged`, `TurnExecuted` и сетевые Connected/Reconnected/Disconnected/PeerReady остаются
доступными внешним менеджерам. `Actions`/`Presentations` — точки внедрения дополнительных действий.

## Совместимость и проверки

WorldState создаёт схему **3**, читает схему **2** с начальными Scene/Planning и параметрами объектов.
Boxes v1 по-прежнему отклоняется. TCP-протокол **3** добавляет Command/CommandReply; все участники должны
обновиться вместе. Формат файлов идентификации не изменён. В файлах сохраняются identity клиента и реестр
сервера; сохранение всего игрового мира между перезапусками Host пока отдельно не реализовано.

Постоянные тесты: `Assets/Tests/Editor/Planning`, сетевые регрессии — `Assets/Tests/Editor/Networking`.
Покрываются связанные планы и права, отмена, подтверждения, невалидные/устаревшие команды, атомарность
исполнения, JSON round-trip, TCP reconnect и порядок patch/reply, запрет прямой записи удалённым клиентом,
реальный drag, меню плана и отсутствие дубликатов менеджеров после reload.

Настройка сцены повторяемая: **Tools → World → Set up game session**. Для новой сцены нужны
WorldSceneController с каталогом prefab и sceneObjects, GridProvider, камера с PhysicsRaycaster,
EventSystem и сцена в Build Settings. Меню текущего прототипа строится из uGUI во время запуска.

Проверка 2026-10-27: полный Unity EditMode-прогон с Play Mode сценариями — **159/159**, включая 13 новых игровых тестов. Процесс завершился с кодом 0. Сохранённый отчёт: [TurnPlanning-tests.xml](../Logs/TurnPlanning-tests.xml). Независимое ревью завершено без оставшихся блокирующих замечаний.
