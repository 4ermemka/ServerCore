# Инвентарь и крафт: устройство и подключение

Система состоит из трёх уровней: данные предметов, модели инвентаря/крафта и
компоненты Unity для настройки и отображения. Начинать создание нового варианта
обычно нужно с asset-ов и prefab-а. Общие классы подбора и списания рецептов менять
не требуется.

## Быстрая проверка примера

Откройте `Assets/Scenes/Test.unity`, включите Play и нажмите **I**. В этой сцене
корневые окна первоначально скрыты для проверки переноса 3D-объектов по сетке;
I переключает их видимость. Сам `Assets/Prefabs/Inventory/InventoryDemo.prefab`
остаётся готовым к обычному запуску активным. Слева вкладки инвентаря на 16 ячеек,
бесконечного каталога и контекста игрока; справа — оружейная мастерская и костёр.
При узком экране корневые окна располагаются вертикально. Чтобы перенести предмет
на другую вкладку, наведите его на закладку во время drag и затем отпустите в ячейке.
Начальное содержимое инвентаря: 4 металла, 4 дерева и 25 крышек.

I — привязка по умолчанию для действия `Inventory.Toggle`. Её можно изменить через
**F1** или кнопку «Управление»; см. [InputSystem.md](InputSystem.md).

Перетащите металл и дерево в мастерскую. В выходе появится **preview** —
предварительный результат. Ресурсы при этом остаются во входных слотах.
«Другой рецепт» переключает обычное оружие (1 металл + 1 древесина) и усиленное
(2 металла + 1 древесина). Подтвердите создание кнопкой или перетащите результат
в свободную ячейку. Только успешное подтверждение расходует ингредиенты.

Из каталога можно сколько угодно брать овощи, уголь и остальные виды предметов.
У костра первый слот принимает овощи, второй — группу `flame_fuel`. Положите оба
ресурса и заберите суп. В примере один суп даёт один опыт готовки, а порог уровня
равен одному: навык сразу станет 2, и появится рецепт хорошего супа. Ещё один
успешный крафт откроет третий вариант. Эти пороги заданы у `PlayerContext` в
Inspector. Рецепты супа расходуют 1/2/3 овоща и 1 топливо соответственно.

Во вкладке «Игрок» меняйте уровень игрока, уровни навыков и флаги чертежей.
Число применяется по Enter или при потере фокуса. Все станции обновляются сразу;
уровень уже созданного оружия при этом не меняется.

В начале переноса выбрана вся стопка. Колесо вниз уменьшает количество, вверх
увеличивает; один шаг меняет его на единицу, диапазон — от 1 до исходного размера.
До Drop предметы остаются в модели. Во время переноса колесо не прокручивает
панель и не приближает камеру.

Перенос на совместимую стопку объединяет предметы до MaxStack; не поместившийся
остаток остаётся в источнике. Частичный перенос в пустую ячейку создаёт новый ItemId,
остаток сохраняет старый. При слиянии сохраняется ItemId назначения.
Различающиеся вид, тип экземпляра, уровень или качество препятствуют слиянию.
Несовместимые занятые ячейки обмениваются только при переносе всей стопки и
разрешении обоих фильтров; частичный обмен отклоняется.

Предварительный результат крафта переносится только целиком. Уже созданный Output
можно разделять. Получение результата в совместимую стопку разрешено, если он
помещается целиком; иначе ингредиенты не расходуются. Каталог выдаёт выбранное
количество в пределах QuantityPerDrag/MaxStack, не изменяя образец.

Открытие первой корневой вкладки включает контекст инвентаря, начало переноса —
вложенный контекст. Отпускание/отмена возвращает предыдущий уровень, закрытие
последнего окна — основной ввод. Cancel сначала отменяет перенос, затем закрывает
окна. Настройка и жизненный цикл описаны в [InputSystem.md](InputSystem.md).

| Prefab в `Assets/Prefabs/Inventory` | Назначение |
| --- | --- |
| `InventoryDemo` | Готовый Canvas с инвентарём, каталогом, двумя станциями и PlayerContext с панелью управления. |
| `InventoryPanel` | Адаптивная панель с TabPanel; работает под Canvas и внутри Body другой вкладки. |
| `InventorySlot` | Одна визуальная ячейка для ручной раскладки или генерации. |
| `GunWorkbench` | Пример конкретной станции с двумя входами и отдельным выходом. |
| `CampfireWorkbench` | Костёр с ручной вертикальной раскладкой входов и тремя рецептами супа. |

Иконки лежат в `Assets/Art/Inventory/Icons`, определения примера — в
`Assets/Data/Inventory`; рецепты — в его подпапке `Recipes`. Всё уже настроено.
Меню `Tools → Inventory → Upgrade Sample Workbenches and Debug Panels` запускает
[InventoryPrefabBuilder](../Assets/Editor/Inventory/InventoryPrefabBuilder.cs):
добавляет отсутствующую демонстрационную конфигурацию, сохраняет существующие
определения, рецепты и внутреннюю раскладку станций. Это миграция конкретного
примера, а не обязательный шаг создания своей станции. Во время игры она не нужна.

## Классы и их обязанности

### Данные предмета — `Assets/Scripts/Inventory/Items`

| Класс | Что хранит и зачем нужен |
| --- | --- |
| `ItemDefinition` | ScriptableObject вида предмета: стабильный `Id`, название, описание, иконка, `MaxStack`, теги. Один asset используется многими экземплярами. |
| `ItemTag` | ScriptableObject смысловой группы, например «Топливо». Даёт группе `Id`, имя и иконку. |
| `ItemInstance` | Конкретная игровая стопка: свой уникальный `ItemId`, ссылка на определение и количество. |
| `ItemInstance<TData>` | Стопка с вашей моделью параметров, например уровнем или качеством. |
| `ItemCatalog` | Сгенерированный список всех определений из Data для каталога в runtime. |

`ItemDefinition.Id` идентифицирует **вид**, а `ItemInstance.ItemId` — конкретный
**экземпляр/стопку**. Два стека дерева имеют один вид и разные `ItemId`.
Переименование asset-а не меняет его идентичность. При дублировании asset-а для
нового вида или новой группы нужно вручную назначить новый `Id`: непустой ID
автоматически не заменяется.

Определения разделяются по ссылке: изменение иконки/описания asset-а касается
всех его экземпляров. Индивидуальные параметры храните в `TData`, а не в asset-е.
`WithQuantity` создаёт остаток с тем же `ItemId` и типом подкласса. Это поверхностная
копия, поэтому данные экземпляра должны быть неизменяемыми либо подкласс должен
правильно копировать их сам. Нулевой остаток представлен пустым слотом.

### Общая модель — `Assets/Shared/Scripts/Systems/InventorySystem`

| Класс | Обязанность |
| --- | --- |
| `InventoryBase<TItem>` | Общая проверка действий, правила `IInventoryActionRule`, события executing/executed/rejected и связь с `TrackableNode`. Сам по себе не хранит ячейки. |
| `InventoryProcessBase<TItem,TRequest>` | База процесса с типизированным запросом, например торговли или крафта. |
| `CraftingStationBase<TItem,TRequest>` | Уточняет вид процесса: `Craft`. Подбор рецептов в нём ещё не реализован. |
| `SlottedInventory<TItem>` | Содержимое ячеек, их число и фильтры; добавление, удаление, перенос, обмен и снимки для SyncSystem. |
| `SlotRule<TItem>` | Predicate допустимого предмета в одной ячейке. Пустая ячейка разрешена всегда. |
| `ICraftingItem<TItem>` | Контракт количества и создания неизменяемого остатка: `Quantity`, `WithQuantity`. |
| `RecipeIngredient<TItem>` | Требование рецепта: какие предметы подходят, сколько нужно и, при необходимости, индекс входного слота. |
| `CraftingRecipe<TItem,TContext>` | Идентификатор и название рецепта, состав, условие доступности, фабрика результата. |
| `RecipeMatcher<TItem>` | Внутренний подбор количеств из входных стопок. Учитывает пересекающиеся требования, не изменяет предметы. |
| `CraftPreview<TItem>` | Предварительный предмет, идентификатор рецепта и внутренний токен актуальности с планом расхода. |
| `CraftCommitRequest<TItem>` | Запрос подтверждения: preview, целевой инвентарь и индекс назначения. |
| `RecipeCraftingStation<TItem,TContext>` | Общее ядро подбора, обновления preview, проверки, расхода и выдачи. Владеет выходом и подписками, использует переданный вход. |

`SlotRule` отвечает на вопрос «может ли этот предмет лежать здесь», а
`IInventoryActionRule` — «допустима ли эта операция». Это разные уровни проверки.
Слотный инвентарь дополняет прежние `ItemStorageBase`/`InfiniteItemStorage`.
Обычный UI использует `SlottedInventory` и его индексы; бесконечный каталог
материализует новые экземпляры через `InfiniteItemStorage`.

| Класс | Обязанность |
| --- | --- |
| `InventoryComponent` | Хранит настройки Inspector и создаёт один `SlottedInventory<ItemInstance>` через свойство `Model`. |
| `SlotSettings` | Настройки отдельного индекса: подсказка и списки допустимых предметов/тегов. |

| `CraftingStationComponent` | Общий контракт станции для UI: preview, выход, выбор рецепта и подтверждение. Унаследованная `Model` — её **вход**. |
| `CraftingStationComponent<TContext>` | База MonoBehaviour: создаёт ядро, наблюдает контекст, безопасно обновляет preview, освобождает подписки в `OnDestroy`. Для произвольной логики оставляет `BuildRecipes`, `BuildContext`, `SetContext`. |
| `ConfiguredCraftingStation` | Готовая станция с `Recipes` и `ContextSource` в Inspector, общим `IPlayerContext` и наградой за успешный крафт. |

### Представления — `Assets/Scripts/Inventory/Views`

| Класс | Обязанность |
| --- | --- |
| `InventoryView` | Связывает `Source.Model` с ячейками в `Content`, обновляет их по событиям, поддерживает ручной и автоматический режим. |
| `InventorySlotView` | Отображает один индекс: фон, иконку, количество, название, подсказку; принимает события мыши. Не владеет предметом. |
| `InventoryDragController` | Хранит один активный drag и временную иконку под курсором; вызывает перенос только при drop. |

| `CraftingControls` | Подключает кнопки выбора/подтверждения, показывает рецепт, параметры результата и ошибки. Не знает состава рецептов. |
| `InfiniteCatalogView` | Показывает образцы с количеством ∞; перенос создаёт новую стопку, входящие переносы запрещены. |
| `PlayerContextView` | Связывает InputField/Toggle с конкретным тестовым PlayerContext; обновляет UI без повторных callbacks. |

[GunWorkbench](../Assets/Scripts/Inventory/Examples/GunWorkbench.cs) и
[CampfireWorkbench](../Assets/Scripts/Inventory/Examples/CampfireWorkbench.cs) —
тонкие подклассы `ConfiguredCraftingStation`. Они не содержат списков предметов,
рецептов и настроек внешнего вида. При необходимости это точки добавления вашей логики.

`Recipes/CraftingRecipeDefinition` — asset рецепта; `RecipeInput` описывает его
ингредиент, `SkillRequirement` — условие навыка. `CraftedItem` и неизменяемый
`CraftedItemStats` сохраняют уровень и качество конкретного результата.
`Context/IPlayerContext` задаёт контракт игрока, `IObservableInventoryContext` —
уведомление `Changed`, а `PlayerContext` — тестовая сценовая реализация.

## Жизненный цикл

### Создание и подключение UI

1. **В редакторе** вы сохраняете prefab, asset-ы, количество ячеек, стартовые
   предметы и ссылки компонентов. Runtime-модели ещё не являются сохранённым
   содержимым prefab-а. `OnValidate` компонентов помечает настройки для обновления;
   он не должен выполнять игровые операции.
2. **Первый доступ к `InventoryComponent.Model`** создаёт модель. Он может случиться
   в `Awake` самого компонента или раньше из другого компонента/UI. Порядок `Awake`
   разных объектов не является контрактом этой системы.
3. **Инициализация модели:** создаются пустые ячейки → `ConfigureSlots` устанавливает
   правила → `InitialItems` создают новые экземпляры и добавляются с проверкой.
   Некорректная стартовая конфигурация вызывает исключение. Поле модели запоминается
   после успешного заполнения. Повторное чтение `Model` не выдаёт предметы заново.
4. **Первый доступ к ядру станции** создаёт `RecipeCraftingStation` из входной модели,
   `BuildRecipes()` и `BuildContext()`. Ядро копирует набор рецептов, создаёт однослотный
   выход, подписывается на изменение входа/выхода и строит доступные preview.
   Компонент также подписывается на `Changed` наблюдаемого контекста. Передаётся
   живой поставщик данных; значения навыков не копируются на весь срок работы станции.
5. **`OnEnable` представлений** вызывает `Rebind`: старые подписки снимаются,
   устанавливаются новые и сразу выполняется `Refresh`. Автоматический View создаёт
   нужное число ячеек; ручной привязывает существующие по `Index`. Кнопки также
   подписываются кодом. Эти шаги могут сами инициировать ленивое создание модели.
6. **Во время работы** UI обновляется по `SlotsChanged` и `PreviewChanged`.
   `LateUpdate` отслеживает смену источников/ссылок представлений. Изменения Inspector,
   помеченные `OnValidate`, применяются компонентами в `Update`.

### Обычный перенос

`BeginDrag` запоминает модель, индекс и неизменяемый экземпляр, создаёт иконку без raycast и
**оставляет настоящий предмет на месте**. При отпускании над другой ячейкой:

1. Контроллер удаляет временное состояние drag до уведомлений модели.
2. Целевой View проверяет, что активен и допускает drop.
3. Захваченная операция проверяет прежний источник и экземпляр. Изменение количества
   после начала drag тоже делает операцию устаревшей; выбранное количество передаётся в модель.
4. `TryMoveTo` проверяет индексы, фильтры, уникальность предметов и правила действий
   с обеих сторон. Для занятого назначения также проверяется обратная сторона обмена.
5. После `ActionExecuting` проверки повторяются. Затем обеим моделям присваивается
   новое состояние, и только после этого отправляются уведомления и `ActionExecuted`.

Отпускание вне ячейки, потеря фокуса или отключение источника просто отменяют drag:
возвращать ресурс не требуется, он ещё не покидал исходный слот.

### Контракт стопки и собственные параметры

`IStackableItem<TItem>` расширяет ICraftingItem: добавляет MaxStack,
`CanStackWith(other)` и `WithStack(quantity, itemId)`. WithQuantity сохраняет
идентификатор остатка, WithStack создаёт копию с переданным идентификатором.
Предмет и все его параметры считаются неизменяемыми. Ядро не знает ItemDefinition
и использует этот контракт; предметы без него перемещаются как целые экземпляры.

Базовый ItemInstance объединяет одинаковые определения. ItemInstance<TData>
дополнительно использует EqualityComparer<TData>; для ссылочных параметров задайте
равенство по значению, если отдельно созданные равные данные должны объединяться.
CraftedItemStats сравнивает Level и Quality.

Неизвестные подклассы ItemInstance по умолчанию не объединяются, чтобы не потерять
неучтённые поля. Разрешите слияние через `SupportsStackMerging` и переопределите
CanStackWith с проверкой собственных параметров. Вызывайте base.CanStackWith,
чтобы сохранить сравнение типа и определения. Разделение сохраняет фактический
тип и поля через копирование; ссылочные поля должны быть неизменяемыми.

`TryMoveTo(target, from, to, quantity)` переносит часть, значение -1 означает всё.
При нехватке места в совместимом назначении переносится доступная часть.
`TryAdd` и получение крафта принимают весь предмет либо отклоняются. При
автоматическом выборе сначала ищется подходящая неполная стопка, затем пустой слот;
распределение одной выдачи по нескольким слотам не выполняется.

API наследников View изменился: CaptureTransfer возвращает делегат
`InventoryTransfer(target, targetIndex, quantity)`. В нём проверяйте актуальность
захваченного источника и передавайте количество модели. GetDragQuantity задаёт
верхнюю границу, CanSplitDrag разрешает изменение колесом. Для preview крафта
CanSplitDrag возвращает false. Старые вызовы TryTransferTo с тремя аргументами
сохранены; четвёртый аргумент выбирает количество.

Для старых prefab-ов доступна команда **Tools → Inventory → Upgrade input contexts**.
Она добавляет координатор на InventoryDemo и меняет тип ScrollRect, сохраняя
fileID, параметры прокрутки и ссылки UI. Несколько координаторов одного источника
делят единственную сессию и пару контекстов (окна/перенос).

### Крафт: от ресурсов до выдачи

1. Перенос ресурсов меняет входную модель. Ядро получает `SlotsChanged`.
2. Для каждого доступного по контексту рецепта `RecipeMatcher` ищет распределение
   количеств. Фабрика создаёт предварительный предмет. Входы не меняются.
3. `CraftingResultView` показывает выбранный preview, хотя `Output[0]` пока пуст.
   Несколько доступных рецептов можно переключать. Фабрика не вызывается на каждом
   кадре: preview кэшируется до изменения состояния.
4. Drag результата захватывает **этот конкретный preview**. `TryClaim` проверяет
   владельца, поколение, версию входа, условие рецепта, план расхода и назначение.
   Смена контекста/ресурсов/правил/выбора делает прежний preview недействительным.
5. При успешном подтверждении ядро одновременно присваивает остатки ингредиентов
   и результат целевому инвентарю. При отказе не применяется ни одна часть изменения.
6. Кнопка `TryConfirm` использует тот же путь, но назначением служит `Output[0]`.
   Пока там готовый предмет, новых preview нет. Его последующий перенос — обычное
   перемещение без повторного расхода. Освобождение выхода позволяет построить
   следующий preview по оставшимся ресурсам.
7. `ConfiguredCraftingStation` после успешного подтверждения начисляет опыт один
   раз. `PlayerContext.Changed` обновляет все станции, поэтому новый уровень навыка
   открывает рецепт уже для следующего крафта. Получение готового выхода повторно
   опыт не начисляет. Preview и неудачный drop также не дают награду.
   Если внешний поставщик опыта выбросит исключение, оно попадёт в лог; уже
   завершённый крафт останется успешным. Повторного начисления автоматически нет.

Preview не нужно вручную добавлять через `target.TryAdd(preview.Result)`:
это обошло бы подтверждение и расход. Всегда используйте `TryClaim`/`TryConfirm`.

### Перенастройка, скрытие и уничтожение

| Событие | Что происходит |
| --- | --- |
| `context.Changed` | Перестраивает preview у всех подписанных станций. Если ядро занято операцией/уведомлениями, обновление ставится в очередь до безопасного момента. |
| `SetContext(newContext)` | Меняет поставщика, снимает старую подписку и обновляет preview; поддерживает ту же ссылку. Отменяет отложенную замену из Inspector. |
| `RefreshConfiguration()` | Строит правила на временной пустой модели и атомарно применяет вместимость/правила. При отказе действующая модель сохраняется целиком. Стартовые предметы повторно не добавляются. |
| Отключение View/панели | Отменяется её drag, снимаются UI-подписки. Модель, предметы и подписка станции на контекст сохраняются. |
| Выбор другой вкладки | CanvasGroup скрывает страницу и отключает raycast. View остаётся активным, перенос через закладку продолжается. Подробнее: [ProceduralTabs](ProceduralTabs.md). |
| Повторное включение | UI заново подписывается и показывает текущее содержимое. Начальное содержимое не восстанавливается. |
| `OnDestroy` станции | Снимает подписку на контекст, освобождает ядро и аннулирует preview. Если ядро занято, освобождение откладывается до `BecameIdle`. Возврат ресурсов и сохранение не выполняются автоматически. |
| Новый экземпляр prefab-а / новый запуск | Создаётся новая модель со стартовыми предметами. Продолжение прошлой сессии требует явного восстановления данных. |

Если переопределяете `Awake`, `OnValidate`, `Update` или `OnDestroy` базового
компонента станции, вызывайте соответствующий `base`-метод. Собственные подписки
также снимайте. Не используйте уничтожение объекта как способ сохранения вещей.

## Создание обычного инвентаря

### 1. Подготовьте предметы

Через `Create → Inventory → Item Definition` создайте необходимые виды. Заполните
ID, подпись, иконку, максимальное количество и теги. Для групп используйте
`Create → Inventory → Item Tag`. Иконки должны быть импортированы как Sprite.
Количество в `InitialItems` должно быть от 1 до `MaxStack`.

Для нового ресурса, принимаемого уже существующей группой, достаточно нового
определения с тем же тегом. Правки enum, UI и общего ядра не нужны.

### 2. Подготовьте сцену и prefab

Сохраните копию или вариант `InventoryPanel.prefab` под своим именем. Разместите
под Canvas с `GraphicRaycaster`; для масштабирования используйте `CanvasScaler`.
В сцене нужен активный EventSystem с подходящим модулем ввода. `InventoryCanvas`
подходит для тестового варианта со старым Input Manager; при другом вводе
подключите собственный EventSystem. Отдельная панель сама Canvas не создаёт.

| Поле/компонент | Что назначить |
| --- | --- |
| `InventoryComponent.Title` | Название панели. |
| `SlotCount` | Число ячеек модели. |
| `Slots` | Необязательные настройки конкретных индексов в пределах вместимости. |
| `InitialItems` | Начальные стопки. `Slot = -1` ищет первую пустую совместимую ячейку. Для явных индексов не задавайте две стопки в один слот. |
| `InventoryView.Source` | Этот `InventoryComponent`. |
| `Content` | RectTransform, содержащий визуальные ячейки. |
| `SlotPrefab` | `InventorySlotView` из prefab-а ячейки; обязателен для создания недостающих ячеек в автоматическом режиме. |
| `TitleLabel`, `CountLabel`, `HintLabel` | Необязательные Text для названия, заполненности и описания при наведении. |

Пример иерархии (ScrollRect и маска уже настроены в готовой панели):

```text
Canvas + CanvasScaler + GraphicRaycaster
└── MyInventory + TabPanel + InventoryComponent + InventoryView
    ├── Body
    │   └── Scroll + ScrollRect
    │       ├── Viewport + RectMask2D
    │       │   └── Content + VerticalLayoutGroup + ContentSizeFitter
    │       │       ├── Title / Count
    │       │       ├── Slots + AdaptiveGridLayout
    │       │       │   └── InventorySlotView ...
    │       │       └── Hint
    │       └── Scrollbar
    └── Tabs (закладки дочерних страниц, если они есть)
```

### 3. Выберите раскладку и ограничения

**Автоматическая:** `AutoGenerate = true`, назначены `Content` и `SlotPrefab`.
Размер и интервалы определяет layout-компонент. View переиспользует авторские
ячейки, удаляет лишние и создаёт недостающие по вместимости модели. Индексы
назначаются последовательно по иерархии. Для большого количества оставьте
прокрутку и динамическую высоту содержимого, как в готовом prefab-е.

**Ручная:** `AutoGenerate = false`; разместите ячейки внутри `Content` сами,
назначьте каждой уникальный `Index` от 0 до `SlotCount - 1`. Координаты не влияют
на индекс и не перестраиваются View. Отсутствующий индекс не будет автоматически
дорисован; ячейки вне диапазона будут скрыты. Не используйте layout-компонент,
который сам перемещает вручную расставленные ячейки.

У `InventorySlotView` назначьте фон, иконку, Text названия и количества; описание
необязательно. Фон должен иметь `raycastTarget = true`; декоративные иконки и
подписи не должны закрывать его от событий. Проверяйте также родительские
`CanvasGroup` и порядок перекрывающих панелей.

В `SlotSettings` списки `AllowedItems` и `AllowedTags` работают через **ИЛИ**;
если оба пусты, разрешён любой предмет. `HintItem`/`HintTag` задают только подсказку,
а не фильтр. Явные `Label`/`PlaceholderIcon` имеют приоритет над данными предмета
и группы. Например, для топлива задайте `AllowedTags = [Fuel]` и `HintTag = Fuel`.

## Создание крафт-станции

### Вариант через Inspector

1. Создайте определения входов/выхода через `Create → Inventory → Item Definition`,
   смысловые группы через `Item Tag`. Назначьте иконки, теги, уникальные ID.
2. Создайте каждый рецепт через `Create → Inventory → Crafting Recipe`.
   Заполните состав, результат и условия по таблице ниже.
3. Скопируйте подходящий prefab станции. Можно оставить `ConfiguredCraftingStation`
   или написать пустой конкретный подкласс `MyStation : ConfiguredCraftingStation`.
   `GunWorkbench` и `CampfireWorkbench` устроены именно так.
4. У компонента станции задайте `SlotCount`, массив `Recipes`, настройки `Slots`
   с уникальными индексами. `AllowedItems`/`AllowedTags` — правила входа;
   `HintItem`/`HintTag`, `Label`, `PlaceholderIcon` — независимое оформление.
5. Назначьте в `ContextSource` сценовый компонент, реализующий `IPlayerContext`.
   Если ссылка пуста, станция ищет поставщика сначала в родителях, затем среди
   активных компонентов своей сцены. При нескольких игроках задавайте ссылку явно.
6. Входной `InventoryView.Source` направьте на станцию. Выберите автоматическую
   или ручную раскладку. У выхода `CraftingResultView.Station` укажите ту же станцию,
   назначьте `Content`, одну ячейку с индексом 0 и `ResultSettings` для подсказки.
7. У `CraftingControls` назначьте станцию, входной/выходной View, кнопки и Text.
   Подписки кнопок добавляются кодом: не дублируйте их в `Button.onClick`.
   Сообщения разных состояний настраиваются в строковых полях этого компонента.

Вход и выход — разные модели. Выход не входит в `SlotCount`. Кнопки необязательны:
подтверждение переносом preview работает самостоятельно. Добавление вида ресурса
или рецепта не требует изменения классов; достаточно asset-ов и ссылок в Inspector.

### Поля asset-а рецепта

| Поле | Смысл |
| --- | --- |
| `Id` | Стабильный уникальный ID рецепта внутри станции. При дублировании asset-а измените его вручную. |
| `DisplayName` | Название, которое показывает переключатель рецептов. |
| `Ingredients` | Массив требований: каждое содержит `Items`, `Tags`, `Quantity`, `SlotIndex`. |
| `Items` / `Tags` | В одном требовании подходят перечисленные виды **ИЛИ** любой перечисленный тег. Пустой фильтр ингредиента не принимает ничего. |
| `Quantity` | Сколько единиц расходуется. Требование может собираться из нескольких стопок. |
| `SlotIndex` | `-1` — любые входные ячейки; `0`, `1` и т. д. — конкретная позиция. Порядок массива сам по себе позиции не задаёт. |
| `Result` / `ResultQuantity` | Определение и количество результата; количество не должно превышать `MaxStack`. |
| `UsePlayerLevel` / `Quality` | Уровень из текущего контекста и фиксированное качество. При включённом уровне или качестве не равном 1 создаётся `CraftedItem` с неизменяемыми данными. Иначе — обычный `ItemInstance`. |
| `RequiredBlueprint` | ID нужного чертежа; пустое значение убирает это условие. |
| `RequiredSkills` | Все пары ID навыка / минимальный уровень должны выполняться. |
| `RewardSkill` / `RewardExperience` | Навык и количество опыта за успешное подтверждение; пустой ID или 0 отключают награду. |

Важно различать три настройки: фильтр **слота** определяет допустимое содержимое,
требование **рецепта** — расход, **подсказка** — только внешний вид. Пустые списки
в `SlotSettings` разрешают всё, но пустые списки в ингредиенте ничего не совпадают.

Пример костра: слот 0 допускает овощи, слот 1 — тег `flame_fuel`; `HintTag` второго
слота показывает общую иконку топлива. У рецепта хорошего супа нужны 2 овоща из
слота 0, 1 топливо из слота 1 и навык `cooking` уровня 2. Дерево и уголь можно
сделать взаимозаменяемыми, назначив их определениям один тег топлива.

### Внешний вид без изменения View-кода

Заголовки, размеры, фоны и расположение задавайте в prefab-е. Для пустой ячейки
приоритет такой: явные `SlotSettings.Label`/`PlaceholderIcon`, затем `HintItem`,
затем `HintTag`, затем исходные `Image.sprite`/`Text.text` самой ячейки.
Исходные подписи и иконка запоминаются перед первым показом предмета и
восстанавливаются после освобождения ячейки. Для разных ручных слотов задавайте
разные значения; для автоматических — значения `SlotPrefab` или `SlotSettings`.

`InventorySlotView.ItemColor` и `PlaceholderColor` задают цвета предмета и подсказки
из настроек; собственная иконка ячейки сохраняет авторский цвет и enabled-состояние.
`CraftingControls` содержит отдельные сообщения для отсутствующей станции,
пустого рецепта/описания, готового выхода, готовности крафта и нехватки ингредиентов.
Ошибки действий по-прежнему приходят из модели. Название обычной панели задаёт
`InventoryComponent.Title`, каталога — `InfiniteCatalogView.CatalogTitle`.

### Когда нужен собственный код

Для нестандартных условий/результатов наследуйтесь от
`CraftingStationComponent<YourContext>`, реализуйте `BuildRecipes()` и
`BuildContext()`. Здесь можно использовать произвольные predicates и
`ItemInstance<YourData>`, не ограничиваясь редакторским форматом рецепта.
Для технических ограничений переопределите `ConfigureSlots(inventory)`; вызывайте
базовый метод, если нужны также `Slots` из Inspector. Награды стандартного
`ConfiguredCraftingStation` не подключаются автоматически к произвольному подклассу.

`ConfigureSlots` настраивает **переданный** инвентарь: не обращайтесь в нём к
`Model`/`Station`, иначе во время создания получится рекурсия. Метод вызывается
также на временной пустой модели при проверке конфигурации. Не выдавайте здесь
предметы или опыт. Сохраните вызовы base при переопределении Unity lifecycle-методов.

## Рецепты и внешний контекст

`CraftingRecipeDefinition.Compile()` создаёт описание для общего ядра. Массивы
требований, условий и параметры результата копируются при создании станции.
Изменение самого recipe asset-а/массива `Recipes` в Play не пересобирает текущую
станцию: для таких изменений создайте новый экземпляр или перезапустите Play.
Уровень, навыки и чертежи при этом **живые**, см. следующий раздел.

Пересекающиеся требования (группа и конкретный предмет из неё) не тратят один
ресурс дважды. Лишние предметы и остатки сохраняются. `Condition` проверяет
внешний контекст: недоступные рецепты не попадают в список preview. UI пока не
показывает отдельные причины скрытия каждого заблокированного рецепта.

В программном рецепте `CreateResult` получает снимок **всех** входных ячеек по
индексам и текущий контекст. Фабрика вызывается при перестроении preview, включая
невыбранные варианты. Она не должна выдавать опыт, списывать ресурсы или менять мир.
Случайные параметры могут генерироваться заново при следующем обновлении preview.

## Живой контекст игрока и тестовая панель

`PlayerContext` — MonoBehaviour на отдельном объекте внутри `InventoryDemo`.
В Inspector задаются `InitialLevel`, списки `Skills` и `Blueprints`. Это исходные
значения сценового поставщика; в Play `InitialLevel` также хранит его текущий уровень.
Навык содержит `Id`, `DisplayName`, `Level`, `Experience`, `ExperiencePerLevel`.
Чертёж содержит `Id`, `DisplayName`, `Known`. Перечислений Enum нет.

Для изменения из игры используйте `SetLevel`, `SetSkillLevel`, `SetBlueprint`,
`AddSkillExperience`. Они отправляют `Changed` при реальном изменении. Прямое
изменение списка из кода событие не отправляет; редакторские изменения ловит
`OnValidate` и применяет через `Update`. Все вызовы делайте в игровом потоке.

`PlayerContextView` привязан к конкретной тестовой реализации. Его `LevelInput`,
элементы `Skills` (ID + InputField + Label) и `Blueprints` (ID + Toggle + Label)
задаются в Inspector. Для нового навыка добавьте запись в менеджер и соответствующее
поле в панели; для чертежа — запись и Toggle. Подписи берутся из `DisplayName` менеджера.
Панель не создаёт новые контролы автоматически по изменению списка во время игры.

Станции подписываются на `IObservableInventoryContext.Changed`. Если ядро свободно,
preview пересчитывается сразу. Если событие пришло внутри подтверждения/уведомления,
компонент запоминает обновление и применяет его после освобождения защиты ядра
через `BecameIdle` либо при следующем безопасном обращении/Update. Это исключает
повторный вход в текущую транзакцию. Старый захваченный preview становится
недействительным; ресурс при отказе перетаскивания не расходуется.

Однократные изменения из обработчиков preview также завершаются до возврата из
setter-а контекста. Цепочка ограничена 16 проходами за одно обновление, чтобы
ошибочный подписчик, меняющий контекст бесконечно, не блокировал игровой поток;
остаток сохраняется до следующего безопасного обращения.

Отключение панели не замораживает контекст станции. Замена поставщика снимает
старую подписку, уничтожение станции освобождает её. Готовый результат хранит
собственные уровень/качество: новые данные игрока влияют только на будущий preview.

Чтобы перейти на боевого игрока, реализуйте `IPlayerContext` в своём компоненте:

```csharp
public interface IPlayerContext : IObservableInventoryContext
{
    int Level { get; }
    int GetSkillLevel(string id);
    bool HasBlueprint(string id);
    void AddSkillExperience(string id, int amount);
}
// IObservableInventoryContext: event Action Changed;
```

Назначьте компонент в `ConfiguredCraftingStation.ContextSource` и отправляйте
`Changed` после изменения значимых данных. Если источник ещё не появился при
Awake, настроенная станция обнаружит его позже. Для изолированных тестов и моделей
без MonoBehaviour доступен `station.SetContext(provider)`.

Произвольный generic-контекст тоже может реализовать `IObservableInventoryContext`.
Если он этого не делает, при изменениях вызывайте `SetContext(updatedContext)`
или `RefreshContext()` вручную. `RefreshContext` повторно вызывает `BuildContext`,
но не перестраивает список рецептов. Контекст наблюдается по событиям, его поля
не копируются в отдельный неизменяемый снимок на старте сцены.

## Бесконечный каталог

`ItemCatalogBuilder` автоматически находит `ItemDefinition` и их подклассы среди
asset-ов и sub-assets внутри **`Assets/Data`**. Работает при загрузке редактора,
изменениях файлов этой папки и перед сборкой. Меню
`Tools → Inventory → Refresh Item Catalog` запускает тот же поиск вручную.
Список сохраняется в `Assets/Resources/Inventory/ItemCatalog.asset`; редакторский
поиск через AssetDatabase заменяет ручное перечисление типов и предметов.
В runtime UnityEditor не используется: сборка получает сохранённые ссылки.

`InfiniteCatalogView` назначьте `Catalog` либо оставьте пустым для загрузки
стандартного Resources asset-а. Настройте `Content`, `SlotPrefab`, заголовки и
автоматическую раскладку как у обычной панели; `InventoryComponent.Source` не нужен.
`QuantityPerDrag` задаёт количество выдачи (в примере 10), ограниченное `MaxStack`.

Каталог показывает каждый вид с ∞. При drop `InfiniteItemStorage` создаёт новый
экземпляр с уникальным `ItemId`; целевой `TryAdd` проверяет свободное место и правила.
Образец не расходуется, перенос в занятый/недопустимый слот отклоняется, входящие
переносы в каталог запрещены. Это отладочная выдача обычных `ItemInstance`: для
экземпляров со специальными игровыми данными расширьте фабрику выдачи.

Добавьте asset нового предмета в Data, назначьте уникальный `Id`, иконку, `MaxStack`
и теги — он появится в каталоге без изменения кода. Фильтры станции и рецепты
настраиваются отдельно. Сгенерированный каталог коммитьте вместе с его `.meta`.


## Интеграция с игровой логикой

Все операции вызывайте в игровом потоке. Защита от повторного входа блокирует
изменения участников из их синхронных callbacks; она не делает модель многопоточной.
Если обработчик события должен начать следующий перенос/крафт, запланируйте его
после завершения текущего вызова, например на следующий `Update`.

| Задача | API |
| --- | --- |
| Выдать новый предмет | `inventory.Model.TryAdd(new ItemInstance(definition, amount))`. Проверить `Succeeded`. |
| Переместить существующий | `source.Model.TryMoveTo(target.Model, sourceIndex, targetIndex)`. Не заменять парой Remove/Add. |
| Изменить только вместимость модели | `Model.TryResize(count)`; занятые удаляемые индексы приведут к отказу. |
| Применить Inspector-настройки из кода | Изменить `SlotCount`/`Slots`, затем `RefreshConfiguration()`, проверить `IsAllowed`. |
| Получить показанный результат | `station.TryClaim(preview, target.Model, targetSlot)`; назначением не может быть собственный вход станции. |
| Создать в выходной ячейке | `station.TryConfirm()`. |
| Обновить внешние требования | Методы живого `PlayerContext` / событие `Changed`; для ненаблюдаемого контекста — `SetContext` или `RefreshContext`. |
| Реагировать на содержимое | `Model.SlotsChanged`; читать модель, не менять её повторно в том же callback. |
| Реагировать на успешные действия | `ActionExecuted` модели/ядра; участники одной составной операции имеют общий `OperationId`. Не начислять одну награду по каждому участнику. |
| Показать ошибку | `InventoryOperationResult.Validation.Code/Message` или результат `InventoryValidationResult`. |

`Model.TryResize` не меняет поле `InventoryComponent.SlotCount`. Если используете
компонент как источник конфигурации, меняйте его настройки через
`RefreshConfiguration`, иначе последующее применение Inspector может вернуть
его настроенную вместимость. При отказе Inspector-поля сохраняют запрошенные
значения, а работающая модель — прежние; исправьте конфликт или освободите слоты.

`SlotsChanged`/`PreviewChanged` — уведомления, а не место для отмены операции.
Исключения их подписчиков изолируются. Ошибки обработчиков событий действий
передаются через `ObserverFaulted`. Для запрета операций используйте правила.
Ядро пропускает рецепт, если его условие/фабрика выбрасывает исключение при
построении preview: при отладке отсутствующего результата проверяйте эти функции.

Сейчас пример локальный. `Sync<TItem[]>`, `GetValue`, `BuildSnapshot` и `ApplyPatch`
дают точки интеграции со существующим SyncSystem, но не подключают транспорт,
серверную авторизацию или сохранение автоматически. `ApplyPatch` — путь доверенного
снимка, не пользовательская операция; он не заменяет `TryMoveTo`/`TryClaim`.
Правила слотов и рецепты описываются конфигурацией/кодом, а не этим снимком.

Перед уничтожением станции решите, куда деть её входы и уже созданный выход.
Для сохранения потребуются ID определений, `ItemId`, количества, индексы и данные
конкретных экземпляров; при загрузке восстановите ссылки на определения по ID.
`[Serializable]` на модели не означает автоматическую сериализацию её read-only
свойств Unity. Загрузка/сохранение и возврат ресурсов — отдельная логика игры.

## Проверка настройки и типичные причины отказа

| Симптом | Что проверить |
| --- | --- |
| Не видна панель | Активность объекта, Canvas, anchors/размеры, порядок отрисовки. |
| Нет ячеек | `Source`, `Content`, `SlotCount`, `SlotPrefab` в автоматическом режиме; Index и иерархию в ручном. |
| Не работает drag | EventSystem/модуль ввода, GraphicRaycaster, raycast фона, CanvasGroup и перекрывающие элементы. |
| Вход отвергает предмет | AllowedItems/AllowedTags и технические правила `ConfigureSlots`; при обмене проверяются оба направления. |
| Иконка группы есть, но подходят любые предметы | HintTag — подсказка; ограничение отдельно задаётся AllowedTags или predicate. |
| Preview отсутствует | Ссылки на определения/теги, количества, SlotIndex, контекст/условия, занятый выход, исключение фабрики. |
| Изменённый рецепт не применился в Play | Рецепты компилируются при создании станции. Перезапустите её; динамические условия меняйте через контекст. |
| Изменение игрока не обновляет станцию | `ContextSource`, реализацию `IObservableInventoryContext.Changed` и вызов setter-а; прямые изменения полей из кода не отправляют событие. |
| Нового предмета нет в каталоге | Asset должен быть ItemDefinition или его подклассом внутри Assets/Data, иметь Id и положительный MaxStack. Выполните Refresh Item Catalog. |
| Drop preview отклонён | Занятое/несовместимое назначение, старый preview после изменения данных, попытка выдать в собственный вход. |
| Изменение числа ячеек отклонено | В удаляемых индексах остались предметы либо новые правила отвергают существующие. |
| Подкласс не инициализируется/не освобождает подписки | Переопределён Unity lifecycle-метод без вызова base. |

Проверяйте новый prefab в Play: начальные предметы, перенос и отказ фильтра,
отмену drag, preview без расхода, подтверждение кнопкой, получение готового
результата без повторного списания, изменение контекста, скрытие/повторное открытие.

Автоматические проверки находятся в `Assets/Tests/Editor/Inventory`, сборка
`ServerCore.Inventory.Tests` в EditMode Test Runner. Модельные тесты проверяют
подбор, ограничения, атомарность и callbacks. UI-тесты входят в Play Mode,
используют реальные prefab-ы и raycast, проверяют подтверждение, контекст и
раскладки. Снимки UI сохраняются в `Logs/Inventory`.
